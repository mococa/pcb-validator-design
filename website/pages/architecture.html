Hub and spoke boundaries, request paths, and the data flows that matter. Trace keeps the order and the original package. The spoke keeps derived geometry and validation history.

Main flows

13 steps
  1. Browser requests order context from the spoke.
  2. Spoke retrieves order context, the package manifest, and the assigned manufacturing profile from Trace.
  3. Spoke dispatches a validation job with order ID, revision ID, and file references.
  4. Worker fetches the actual package files from Trace using its own authorized Hub API access.
  5. Worker parses, normalizes and validates the package.
  6. Worker writes derived geometry to object storage.
  7. Worker reports result metadata and findings to the API.
  8. API persists run state and findings in Postgres.
  9. API reads derived geometry from object storage when serving the browser.
  10. API streams validation progress and completion to the browser over SSE.
  11. API returns results and the geometry reference or payload to the browser, which displays the completed results.
  12. Browser uploads a revised package to Trace. The customer triggers validation again from the spoke UI; the spoke reads the new revision through the Hub API and starts a new run.
  13. After the run is persisted, the spoke posts findings and priceable order items to Trace. If Trace is unavailable, this post can be retried without rerunning validation.
Ownership in one line: Trace owns identity, the order, the original package files and revisions, the assigned manufacturing profile, cost roll-up and checkout. The spoke owns interpretation, normalized geometry, runs, DFM rules and derived artifacts, and applies its own ruleset to the assigned profile. Revision upload goes to Trace; the customer triggers validation again from the spoke UI, and the spoke reads the new revision through the Hub API. Findings and items are posted only after the run is persisted, so a failed post can be retried without rerunning validation. The worker fetches files with its own authorized Hub API access and never talks to the database directly; it reports metadata and findings to the API, which persists run state.

The diagram is a design proposal, not a deployment snapshot. The browser never parses Gerber; it renders normalized geometry returned by the spoke.
